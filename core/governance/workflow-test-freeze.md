# V-MAX Workflow Test Freeze 1.0

## 定位

本規則用於「重跑／測試／驗證 V-MAX 工作流」的情境。

當教師的意圖是測試既有流程是否正確執行時，AI 的角色是 **執行者與記錄者**，不是系統設計者。

核心原則：

> 測試時先忠實跑流程；發現偏差先記錄，不要邊跑邊改規格。

---

## A. 啟動條件

若教師出現以下任一明確意圖，進入 `TEST_FREEZE`：

- 重新跑一次
- 重跑
- 測試工作流
- 驗證流程
- 從頭測
- 不沿用前次進度
- 依現行規則跑一次
- 先跑看看

也可由教師直接指定：

```text
TEST_FREEZE ON
```

---

## B. TEST_FREEZE 行為

進入後：

1. **不得自行新增規則。**
2. **不得自行修改 GitHub / Skill / Core / YAML / Schema。**
3. **不得因某一步輸出不理想就當場升級系統。**
4. 必須依目前已存在且最新的正式規格執行。
5. 發現偏差時，只做：
   - 指出「預期 vs 實際」
   - 標記 `REGRESSION / MISSING_INTERFACE / RULE_CONFLICT / DATA_ERROR`
   - 停在原本的 HOLD
   - 等教師決定要「繼續測」或「退出測試後修規則」
6. 不得把「測試中的暫時修正」偷偷寫回全域規則。
7. 不得因教師指出問題就自動把問題視為全域新規則。

---

## C. 教師確認與規則修改分離

### 測試中的教師回覆

例如：

```text
這裡怪怪的
這裡少了推薦指數
這裡不該是 JSON
形近字分析不見了
```

在 `TEST_FREEZE` 下，以上先視為 **測試發現**，不是「請修改系統」。

AI 應回：

```text
已記錄偏差：XXX。
目前停在 STEP X / HOLD X，不往下跑。

A｜繼續依現行規格測試
B｜退出 TEST_FREEZE，修正這個規則
```

若教師沒有選 B 或明確說「修改／修正規則／更新技能／寫進系統」，不得寫入 repo。

---

## D. 允許修改的明確觸發詞

只有教師明確表達下列意圖，才可離開測試凍結並修改規格：

- 幫我修改規則
- 寫進技能
- 更新核心
- 修正工作流
- 把這條加入系統
- 更新 GitHub
- 升級這個模組

若語意只是「這裡怪怪的／怎麼不見了／為什麼變這樣」，一律先診斷，不直接升級。

---

## E. 新對話行為

新對話若教師明確說「重跑、測試、從頭開始」，即使沒有前一對話的局部狀態，也應：

1. 讀取正式 Workflow / Skill 的最新版本。
2. 啟用 `TEST_FREEZE`。
3. 從指定 STEP 開始執行。
4. 不主動重構流程。
5. 不把模型自己的改進衝動當成教師需求。

若無法確認某個規則，標記 `SPEC_UNCLEAR` 並停等，而不是自行補規則。

---

## F. HOLD 顯示原則

測試模式下每個 HOLD 只做兩件事：

- 呈現該步依正式規格應有的教師可讀輸出。
- 等教師確認／微調。

禁止在 HOLD 中突然出現：

- 「我順便幫你升級了…」
- 「我已經把這條寫進 GitHub…」
- 額外的新模組／新代號／新流程

除非教師明確要求修改系統。

---

## G. 測試偏差紀錄

可記錄：

```yaml
test_observation:
  step:
  expected:
  actual:
  classification: REGRESSION | MISSING_INTERFACE | RULE_CONFLICT | DATA_ERROR | SPEC_UNCLEAR
  blocks_progress: true | false
  repo_change_requested: false
```

此紀錄是測試報告，不代表全域規則已改。

---

## H. 結束條件

以下任一情況結束 `TEST_FREEZE`：

- 教師明確說「測試結束」。
- 教師明確要求進入系統修改／升級。
- 該次完整回歸測試完成。

---

## 核心金句

> 測試工作流時，AI 要像測試員，不要像熱情過頭的產品經理。

> 先證明舊規則能不能跑，再決定要不要改規則。
